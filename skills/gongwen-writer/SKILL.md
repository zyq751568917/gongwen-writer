# 公文写作与排版

面向党政机关公文的三件事：**写**（起草正文）、**排**（套 GB/T 9704-2012 版式）、**校**（出具合规报告）。
排版由脚本确定性执行，你负责内容、角色判断和依据把关。

## 任务分流

| 用户诉求 | 路径 | 产出 |
|---|---|---|
| 写一份新公文 | 起草 → 排版 → 校验 → 确认 → 交付 | docx + 依据来源 |
| 把材料改成规范公文 | 抽取 → 角色推断 → 排版 → 校验 → 确认 → 交付 | docx + 内容改动清单 + 版式改动清单 |
| 检查现有公文格式 | 抽取 → 校验 | 合规报告（不产出 docx） |

## Inputs to collect

以下要素决定版式与结构。**能推断的先推断并写进确认单**，只有真正影响成稿的才问；一次性问齐，不要逐条追问。

- 文种（决定结构与用语，见 `references/doc-types.md`）
- 发文机关/落款单位全称或规范化简称
- 成文日期
- 是否上行文（决定是否要签发人、发文字号位置）
- 主送机关；抄送机关；附件清单
- 发文字号（机关代字〔年份〕序号）
- 输出文件名；是否同时出 PDF
- 是否需要红头（发文机关标志）

## Procedure

1. **判定路径**：写新稿 / 改稿排版 / 仅校验。

2. **读取材料**（Word/Excel/PPT/PDF）：
   ```powershell
   powershell -ExecutionPolicy Bypass -File <skill_dir>\scripts\extract-text.ps1 -Path "材料路径" -OutFile "材料.txt"
   ```
   扫描件 PDF 无文本层，脚本会明确提示，不要凭猜测补内容。

3. **定结构与依据**：
   - 按 `references/doc-types.md` 选文种模板与要素顺序。
   - 结构或收尾语存疑时，按 `references/source-policy.md` 检索官媒/政府官网范例，**记录可点链接**；查不到就说明"未检索到官方范例，按国标通用要求处理"，不要编造条款号或 URL。

4. **写正文**（`references/official-style.md`）：
   - 书面庄重、简明准确，总—分结构。
   - 层次序数固定为 `一、`→`（一）`→`1.`→`（1）`，字体依次黑体、楷体、仿宋、仿宋。
   - 用具体事实替代抽象名词，删掉无实指段落。
   - 文风按公文语体把握（书面、庄重、简明）。**风格精简（去 AI 味一类）属用户可选项**：决定前先按 `references/official-style.md` 第 5 节向用户说明会怎么改，再按用户的选择执行；用户没表态就保留原表述，不擅自删改。

5. **先出文本，不出文件**：把成稿全文直接贴在对话里——公文标题、主送机关、正文、附件说明、发文机关署名与成文日期——并附版式参数摘要、依据来源、待确认要素。**此时不生成 spec.json / docx / PDF**：文档是成稿定下来之后才做的事。
   - 用户提修改意见：在这份文本上改，再贴一次新版；同样不出文件。
   - 用户明确说"直接出 Word，不用先看文本"时可跳过本步，但要在交付说明里写明跳过了文本确认。

6. **用户确认成稿后**，才生成 spec.json（`references/spec-schema.md`）：每个段落一个 block，标好 role。文本与角色判断归你，排版归脚本。

7. **排版**（Windows + Word 优先，无 Word 用 Node 兜底）：
   ```powershell
   powershell -ExecutionPolicy Bypass -File <skill_dir>\scripts\format-gongwen.ps1 -SpecPath "spec.json" -OutputPath "输出.docx"
   ```
   无 Word 环境：`node <skill_dir>\scripts\ooxml-format.mjs --spec "spec.json" --out "输出.docx"`
   兜底引擎同样输出红色分隔线、版记线与奇偶页页码，但字符网格按 3 号字标定；正文换了字号就要用 verify 复核，并在交付说明里写明。

8. **标点规范化**：
   ```powershell
   powershell -ExecutionPolicy Bypass -File <skill_dir>\scripts\normalize-punctuation.ps1 -Path "输出.docx" -InPlace -ReportPath "标点修改.txt"
   ```

9. **校验**（必做）：
   ```powershell
   powershell -ExecutionPolicy Bypass -File <skill_dir>\scripts\verify-gongwen.ps1 -Path "输出.docx" -JsonPath "校验.json"
   ```
   校验项：页面边距与网格、逐段字体/字号/缩进/行距、西文槽是否为 Times New Roman、页码（宋体 4 号"— N —"、奇偶分侧）、中文语境半角标点、正文是否在首页。**FAIL 项必须清零**才能交付。

10. **交付前确认（不可跳过）**：用问答工具一次性确认清单，用户回复后才生成最终文件。
   确认单必含：文种、发文机关与落款、成文日期、是否上行文、发文字号、主送/抄送/附件、文件名、是否出 PDF、是否需要红头；另加一项可选项——是否做风格精简（问之前先按 `references/official-style.md` 第 5 节说明会怎么改，再让用户定）。

11. **交付**：docx 文件 + 说明三段。
    - 排版说明：页面、字体矩阵、版式要素（简述，不复述全文）。
    - 依据来源：引用的国标条款与官媒范例链接（见 `references/source-policy.md`）。
    - 改稿时另附：内容改动逐条清单（哪段改了什么）+ 版式改动清单。不静默改写正文。

## 脚本调用约定

- 所有脚本只吃文件参数、只写输出文件，不保存会话状态；同一输入重复执行结果一致。
- Word COM 是单实例串行资源：**排版任务排队执行，不要并行跑多个 format 脚本**。
- 需要 PDF 预览时：`powershell -ExecutionPolicy Bypass -File <skill_dir>\scripts\export-pdf.ps1 -Path "输出.docx" -OutputPath "输出.pdf"`
- 脚本路径里的 `<skill_dir>` 替换为实际技能目录；Windows 用反斜杠或正斜杠均可。

## Windows (win32) 平台要点

- `.ps1` 脚本是 **UTF-8 with BOM**：Windows PowerShell 5.1 会把无 BOM 的 UTF-8 按 ANSI 解码，脚本里的中文（字体名、提示语）会变乱码并导致字体判定错误。改脚本后确认 BOM 还在。
- **字体检测只提示不阻断**：四款方正字体常以"按用户安装"方式注册（HKCU），新起的进程有时枚举不到，脚本会警告"未能确认已安装"但仍按标准字体名写入文档，不做任何替代。要强制拦截加 `-StrictFont`（缺字体退出码 3）。
- 控制台输出为 UTF-8；解析报告直接读 JSON 文件，不要依赖控制台转述。
- 本机没有 Python 与 LibreOffice：官方 docx/pdf 插件技能的依赖门禁在本机会失败，本技能的脚本不依赖它们。
- 报告类输出（JSON）不带 BOM，文本类输出带 BOM。
## Output contract

- **两阶段交付**：第一阶段在对话里直接输出成稿纯文本与版式参数，**用户确认成稿前不生成任何文档文件**（docx / PDF 一律不出）；第二阶段才生成 .docx。
- **默认输出 .docx**（第二阶段）；文件名建议《发文机关关于××事由的文种（YYYYMMDD）.docx》。
- 对话中同时给出：排版参数摘要、依据来源链接、标点与内容改动清单。
- 未经用户确认成稿不产出文档；只有 spec.json、校验报告等中间产物可先行生成。

## Failure handling

- **字体缺失**：报告缺哪一款，保留文字不变，交用户决定；不静默换成仿宋_GB2312 等近似字体。
- **Word COM 起不来**：降级 `ooxml-format.mjs`，并在交付说明列出未完成版式项。
- **扫描件 PDF**：明确报"无文本层，需 OCR"，不要编内容。
- **spec.json 有未知角色或缺字段**：脚本报非零退出并指出字段，改 spec 后重跑。
- **校验有 FAIL**：先修再交付；修不动的写进交付说明，由用户决定。
- **排版脚本报"缺少字体"**：先看是不是按用户安装的字体在新进程里枚举不到；确认缺字体就报告用户，不要换近似字体顶替。
- **要素拿不准**（文种歧义、落款、日期、红头、是否出 PDF）：进确认单问用户，不猜。
- **要不要做风格精简**：这是用户个人取向。先说明再问，用户没表态就不改，不擅自删改他的表述。
- **用户还没确认成稿就催着要文件**：先把成稿纯文本贴出来请其确认；只有用户明确说"不用先看文本"才直接出文档。

## Examples

**例 1：起草请示并排版**

输入："帮我写一份关于××项目资金申请事项的请示，发文单位是无锡市××集团，日期 2026年11月25日，附件是可行性研究报告。"

动作：抽取材料 → 判定为上行文请示（一文一事）→ 问齐文号与主送机关 → 起草正文（请示缘由、请示事项、请求语）→ **在对话里贴出成稿纯文本 + 版式参数 + 依据来源，等用户定稿** → 用户确认 → spec.json → 排版 → 标点规范化 → 校验清零 → 交付 docx。

**例 2：改稿排版**

输入："把这份.docx改成规范公文格式，正文不要动。"

动作：抽取 → 角色推断（标题/一、/（一）/正文/落款/日期/附件说明）→ 只调结构与版式 → **先把改后的正文贴出来让用户确认内容（此阶段不出文件）** → 用户确认 → 排版 → 校验 → 交付，附"内容改动：无"与版式改动清单。
